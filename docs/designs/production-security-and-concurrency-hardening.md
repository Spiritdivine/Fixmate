## 1. Problem Statement
The Artisan (Fixmate) platform is operating in **live pilot/beta handling real money and escrow contracts**. A rigorous `gstack` pre-landing review uncovered critical vulnerabilities and concurrency flaws across authentication, transaction security, and database locks:
1. **Unverified OAuth Audience & Forged Signatures:** Google token verification omits `payload.aud` validation; Apple token verification relies on unverified `jwt.decode` without JWKS signature verification.
2. **Transaction PIN Brute Force & Overwrite:** The 4-digit financial transaction PIN lacks rate limiting and lockout counters, and existing PINs can be overwritten without current password/PIN validation.
3. **Step-Up Token TOCTOU Race:** In `requireStepUpAuth`, `redis.get()` followed by `redis.del()` allows concurrent replay attacks.
4. **Change Order & Payout Concurrency:** Missing pessimistic database locks enable duplicate milestone creation and bypassing daily 24-hour KYC withdrawal caps under parallel requests.

In a live-money platform, these are existential solvency and trust vulnerabilities.

---

## 2. Demand Evidence & Real-World Stakes
- **Context:** Artisan has live beta users (clients and artisans) initiating contracts, depositing funds, and executing withdrawals.
- **Risk Profile:** In a peer-to-peer artisanal service economy, an account takeover or stolen escrow payout destroys platform reputation and incurs direct corporate liability.
- **Decision:** Zero tolerance for security lag; apply **Strict Production Hardening** immediately.

---

## 3. Status Quo
- Current code relies on basic validation without cryptographic verification of third-party public keys.
- Check-then-act logic in Prisma is performed outside transactions, exposing milliseconds-wide race windows to fast HTTP clients.
- Rate limiting was omitted on the new `/auth/pin/*` endpoints.

---

## 4. Constraints
1. **Zero Database Migrations / Schema Changes:** Must work with the existing PostgreSQL schema and Prisma models (`User`, `Wallet`, `ContractChangeOrder`, `Milestone`, `PayoutRequest`).
2. **Backward Compatibility for Mobile Apps:** The mobile client must continue functioning without requiring immediate app store re-submissions (response shapes remain stable).
3. **Developer Sandbox Preservation:** In non-production environments (`NODE_ENV !== 'production'`), mock tokens (e.g. `mock-google`, `mock-apple`) must continue to work for local developer velocity.

---

## 5. Recommended Architecture & Implementation Details

### A. Cryptographic OAuth Token Verification (`src/services/social-auth.service.js`)
- **Google:**
  - In production, assert `payload.aud` matches either `env.GOOGLE_CLIENT_ID`, `env.GOOGLE_IOS_CLIENT_ID`, or `env.GOOGLE_ANDROID_CLIENT_ID`.
  - Reject tokens with mismatch or missing audience with HTTP 401.
- **Apple:**
  - Integrate `jwks-rsa` to retrieve signing keys from Apple's public endpoint (`https://appleid.apple.com/auth/keys`).
  - Verify signature using RS256 with `issuer: 'https://appleid.apple.com'` and `audience: env.APPLE_BUNDLE_ID`.
  - Cache public keys in memory with 24-hour TTL to avoid latency on sign-in requests.

### B. Transaction PIN Protection & Lockout (`src/services/auth.service.js`, `src/middlewares/auth.middleware.js`)
- **Rate Limiting:** Mount `authRateLimiter` on `/auth/pin/set`, `/auth/pin/change`, and `/auth/pin/verify`.
- **Lockout Mechanism:**
  - Before comparing hash in `verifyTransactionPin`, check Redis key `pin_lockout:${userId}`. If present, throw HTTP 403 (`Account locked for 15 minutes due to too many failed PIN attempts`).
  - On incorrect PIN, increment `pin_attempts:${userId}` (expire 900s).
  - If counter >= 5, set `pin_lockout:${userId}` = `LOCKED` (expire 900s) and reset attempts.
  - On successful PIN verification, delete `pin_attempts:${userId}`.
- **Overwrite Guard:** In `setTransactionPin`, check `if (user.transactionPinHash)` and reject with `ApiError.badRequest('PIN already set. Use change PIN instead.')`.
- **Atomic Step-Up Token Consumption:** In `requireStepUpAuth`, execute `const deleted = await redisCache.del(key)`. Only proceed if `deleted === 1 || deleted === true`.

### C. Pessimistic Concurrency Locks (`src/services/contract.service.js`, `src/services/wallet.service.js`)
- **Change Orders:**
  - In `respondToChangeOrder`, move lookup inside `prisma.$transaction`.
  - Query with row-level lock:
    ```sql
    SELECT id, status, additional_amount, reason, contract_id
    FROM contract_change_orders
    WHERE id = $1::uuid FOR UPDATE
    ```
  - Verify `status === 'PENDING'` under the lock before setting `APPROVED` and creating amendment milestones.
- **Withdrawals (KYC Daily Limit):**
  - In `requestPayout`, compute `past24hPayouts` sum **inside** `prisma.$transaction` while holding `SELECT ... FROM wallets WHERE user_id = $1::uuid FOR UPDATE`.
  - Prevents burst concurrent requests from exceeding the ₦50k/₦1m daily thresholds.

### D. Collision-Resilient Social Registration (`src/services/auth.service.js`)
- In `socialLogin`, wrap new user creation in a retry block (up to 3 attempts) with a fresh random number or handle unique constraint `P2002` gracefully on `phoneNumber`.

## 6. Verification Plan

| Area | Test Execution | Success Criteria |
|---|---|---|
| **Google Auth** | Send token with mismatched `aud` claim | HTTP 401 `Invalid token audience` |
| **Apple Auth** | Send forged JWT with unverified signature | HTTP 401 `Invalid Apple token signature` |
| **PIN Lockout** | Send 5 incorrect PINs consecutively | 5th returns 400; 6th returns 403 `Account locked for 15 minutes` |
| **Step-Up Replay** | Send 2 simultaneous requests with 1 token | Exactly 1 returns 200, 1 returns 403 `Token already consumed` |
| **Change Order** | Send 2 parallel approvals for same change order | Exactly 1 creates milestone and increments totalAmount |
| **Payout Cap** | Send 2 concurrent withdrawals totaling > daily limit | Second request is rejected with limit error |
